### concern `local-storage-cross-tab-race`
**File:** lib/msal-browser/src/cache/BrowserCacheManager.ts
**Step:** review-fresh-eyes | **Action:** fix | **Confidence:** medium

[json-extracted] Nonce write serialization is held only in an in-memory WeakMap and does not coordinate localStorage writes across tabs. Separate browsing contexts have separate WeakMaps but share the same localStorage. Concurrent challenge responses can both read the old value and then overwrite each other; equal-millisecond timestamps are especially vulnerable because the newer-value guard only rejects strictly older writes. Suggestion: Add cross-context conflict handling, such as a storage-backed version/order check immediately before committing, and cover concurrent localStorage writers from separate contexts.

### concern `stored-nonce-never-consumed`
**File:** lib/msal-browser/src/cache/TokenCache.ts
**Step:** review-fresh-eyes | **Action:** fix | **Confidence:** high

[json-extracted] loadDpopNonce persists the resource-server nonce, but no production code reads getDpopNonce when generating a subsequent DPoP proof. After a resource server returns a DPoP-Nonce challenge, an application can call this new API and retry token acquisition, but the generated proof still omits the stored nonce. The retry therefore receives the same challenge again, making the public persistence API behaviorally ineffective. Suggestion: Read the cached resource-server nonce during DPoP resource-proof generation and pass it into the proof parameters. Add a challenge-load-reacquire test that asserts the resulting proof contains the nonce.

### suggestion `missing-nonce-cache-telemetry`
**File:** lib/msal-browser/src/cache/TokenCache.ts
**Step:** review-fresh-eyes | **Action:** fix | **Confidence:** high

[json-extracted] The new public cache operation has no performance measurement or cache success/failure telemetry. Persistence failures, quota recovery, and invalid challenge values affect DPoP reliability but are currently invisible to the library's performance telemetry, preventing diagnosis of repeated nonce challenges in production. Suggestion: Wrap the operation with the repository's performance instrumentation, include a correlation ID, and record sanitized cache outcome fields without logging the nonce.

### concern `failed-write-evicts-valid-nonces`
**File:** lib/msal-browser/src/cache/BrowserCacheManager.ts
**Step:** review-fresh-eyes | **Action:** fix | **Confidence:** high

[json-extracted] Existing nonce entries are removed before the replacement write is known to succeed. At the capacity boundary, a non-quota setItem failure loses the oldest valid nonce even though no new value was stored. Under unresolved quota pressure, the retry loop can remove every nonce and still throw, leaving the cache unnecessarily empty. Suggestion: Avoid destructive pre-eviction for non-quota failures and preserve or restore removed entries when the new value cannot be persisted.

### 🟡 `older-write-purges-newer-origins`
**File:** lib/msal-browser/src/cache/BrowserCacheManager.ts
**Step:** review-logic | **Action:** fix | **Confidence:** high

[json-extracted] A delayed nonce write validates all retained entries using the delayed entity's older timestamp, causing newer nonces for other origins to be classified as future-dated and deleted. The write queue is shared only within one JavaScript realm. If another tab writes origin B at time T2 while an origin A write created at T1 is awaiting hashing, the T1 write can resume later and call getDpopNonceEntries(nonceType, T1). The valid origin-B entry has lastUpdatedAt T2, so isDpopNonceEntityValid rejects it as future-dated and the enumeration removes it. The same-origin freshness check does not protect entries under different cache keys. Suggestion: Use the actual current time when validating retained entries during cleanup, rather than entity.lastUpdatedAt. Keep insertion ordering and eviction comparisons separate from entity-validity time, and add a test with an older delayed write and a newer nonce under a different origin.
