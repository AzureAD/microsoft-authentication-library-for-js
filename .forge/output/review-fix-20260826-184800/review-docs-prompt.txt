# review-docs

> **⚠️ When running inside a loop:** Every finding MUST be registered by calling the `report_finding()` tool — it is an actual tool in your tool list, not a text format. The fix-agent and acceptance criteria only see tool-registered findings.

> **📂 Getting the PR diff:** Use `get_changed_files()` to list changed files and `get_diff(<file>)` to read per-file diffs. These MCP tools use the correct merge-base diff and return only files in the PR. Do **not** run raw `git diff` via powershell — `git diff origin/main..HEAD` uses two-dot syntax which includes unrelated changes from main's history.

Scan changed documentation for **correctness**, not prose taste. This reviewer closes a
common gap: docs that ship broken links, stale references, or code samples that no longer
run because the code they describe changed in the same PR.

**Default scope:** files whose path matches `\.(md|mdx|rst)$`. Skip everything else — other
reviewers handle non-doc files.

## What You Review

- **Broken links & paths** — internal relative links (`./foo.md`, `../dir/bar`) that point at
  files which don't exist, were moved, or were renamed in this PR. Anchor links (`#section`)
  to headings that don't exist in the target.
- **Stale references** — mentions of files, functions, classes, CLI flags, config keys, env
  vars, or API endpoints that were renamed or removed by other files in the same PR. Cross-check
  doc claims against the code diff.
- **Incorrect code samples** — fenced code blocks with syntax errors, wrong imports, wrong
  package/module names, parameters that don't match the current signature, or shell commands
  that reference the old name/flag. Verify samples against the changed code where possible.
- **Structure that breaks rendering** — skipped heading levels (H2 → H4), duplicate H1s,
  malformed tables, unterminated code fences, broken front-matter (invalid YAML).
- **Doc/code drift** — new public surface (a new command, flag, endpoint, or exported symbol)
  added in the PR with no corresponding doc update, or a doc describing behavior the diff just
  changed.
- **Terminology / cross-file consistency** — the same concept named inconsistently within the
  changed docs, or a table of contents / index out of sync with the sections it lists.
- **Dead external links** — obviously broken external URLs (report as `info`/`low`; do not
  fetch the network).

## What NOT to Review

- Prose style, tone, voice, or word choice — this is not a copy-editing pass.
- Subjective phrasing or "I'd word this differently" nits.
- Spelling of proper nouns unless clearly wrong and material.
- Non-documentation files (source, tests, CI, manifests) — other reviewers own those.
- Pre-existing doc issues untouched by this diff (note them separately, do not file findings).

## How to Report

Use `report_finding()` for each validated issue.

- **id** — kebab-case identifier (e.g., `broken-link-getting-started`)
- **severity** — 🔴 doc actively misleads or a link/sample is broken in a way that blocks a
  reader from completing a documented task; 🟡 materially incorrect or stale content;
  🟢 minor correctness gap with an easy workaround; ℹ️ observation or polish
- **file** / **line** — exact location
- **action** — `fix` for correctness problems, `info` for observations
- **details** — what's wrong, the evidence (the target that doesn't exist, the code the sample
  contradicts), and the concrete fix
- **confidence** — `high` (verified against the diff/tree), `medium` (likely but not fully
  traced), `low` (pattern match)

Only flag issues in the changed docs. Note pre-existing problems separately without registering
them as findings.

### Example finding

```
report_finding(
  id: "stale-cli-flag-quickstart",
  severity: "🟡",
  file: "docs/quickstart.md",
  line: 63,
  action: "fix",
  details: {
    problem: "Sample uses `--out-dir`, but this PR renamed the flag to `--output-dir` in cli.ts.",
    reasoning: "The changed cli.ts drops `--out-dir`; a reader copy-pasting this command hits an unknown-flag error.",
    suggestion: "Update the sample to `--output-dir` to match the renamed flag."
  },
  confidence: "high"
)
```

## Quality bar

- Review only issues introduced or worsened by the current diff.
- Ground every finding in evidence: name the missing target, the contradicting code, or the
  broken structure. "Might be outdated" is not enough.
- Do not flag taste or style differences.
- A review with 3 real correctness findings beats one with 30 wording nits.

## How to Report Findings
After completing your review, output a JSON array as your **final message**.
This is the ONLY output the downstream fix-agent sees. Everything else is discarded.

If you found issues, end your response with exactly this format:
```json:findings
[
  {
    "id": "null-deref-auth-handler",
    "severity": "🔴",
    "file": "src/Auth/Handler.cs",
    "line": 42,
    "action": "fix",
    "details": {
      "problem": "ctx.User can be null when auth is skipped but is dereferenced without a null check on line 42",
      "reasoning": "When authentication is bypassed via AllowAnonymous, the middleware sets ctx.User to null. Line 42 calls ctx.User.Identity.Name without checking, causing NullReferenceException for anonymous requests.",
      "suggestion": "Add a null check: if (ctx.User?.Identity?.Name is not null) before dereferencing, or return a 401 early when User is null."
    },
    "confidence": "high"
  }
]
```

If no issues found, output an empty array:
```json:findings
[]
```

Field reference:
- **id** — short kebab-case (e.g., `missing-null-check`); your skill may specify a load-bearing format
- **severity** — `🔴` critical, `🟡` concern, `🟢` suggestion, `ℹ️` info
- **file** — exact path relative to repo root, or `null` for file-level
- **line** — 1-based line number, or `null` for file-level
- **action** — `fix` (should be fixed) or `info` (observation only)
- **details** — structured object with three subfields:
  - **problem** — what's wrong (the issue itself, one sentence)
  - **reasoning** — why it matters (trace the logic, explain the consequence)
  - **suggestion** — concrete fix (what to change, where)
  - Legacy: a plain string is still accepted but the structured format is preferred
- **confidence** — `high` (verified), `medium` (likely), `low` (suspected)
