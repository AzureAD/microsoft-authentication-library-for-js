## Current Findings to Fix

### 🟡 `ambiguous-dpop-response-treated-as-l1`
**File:** lib/msal-browser/src/interaction_client/PlatformAuthInteractionClient.ts
**Step:** review-fresh-eyes | **Action:** fix | **Confidence:** high

The fallback branch rejects only `attested_chosen === true`, so a response containing merely `token_type: "DPoP"` with no proof, no attestation decision, and no binding key identifier passes as L1. MSAL then signs with its local key and caches the access token under that key even though the broker never affirmed that local binding was chosen. If the response is truncated or produced by an incompatible broker, the returned proof cannot authorize the access token and the bad token is retained. Require an explicit L1 outcome (at minimum `attested_chosen === false`, plus the expected local binding identifier when the contract provides it) before signing or caching.

### 🟡 `broker-dpop-key-outlives-memory-token-cache`
**File:** lib/msal-browser/src/interaction_client/PlatformAuthInteractionClient.ts
**Step:** review-fresh-eyes | **Action:** fix | **Confidence:** high

retainDpopRequestKey deliberately drops all cleanup tracking after an L1 token is written to nativeInternalStorage. That token cache is MemoryStorage and disappears on reload/navigation, while TokenBindingKeyManager stores the key in AsyncMemoryStorage backed by IndexedDB. No access-token eviction occurs when the page's memory is discarded, so the generated key remains persistently orphaned after every page lifecycle. Keep enough durable ownership metadata to reconcile keys when the in-memory native cache disappears, persist the token at the same lifetime, or use a page-local key store for these generated broker partitions.

### 🟡 `dpop-key-ownership-default-breaks-existing-cleanup`
**File:** lib/msal-common/src/cache/CacheManager.ts
**Step:** review-fresh-eyes | **Action:** fix | **Confidence:** high

Existing non-broker DPoP access-token entities never set the new tokenBindingKeyOwnedByMsal field, so the strict `=== true` guard stops removing their MSAL-generated keys. ResponseHandler still creates DPoP AccessTokenEntity values with keyId but without this marker; when those tokens are replaced, expired, or account context is cleared, removeAccessToken now removes the token but leaves its IndexedDB-backed signing key behind. Preserve cleanup for existing/MSAL-generated DPoP entries (including legacy entries without the field), and only suppress removal when ownership is explicitly known to be caller-owned, or populate ownership consistently in every DPoP creation path with migration coverage.

### 🟡 `generated-broker-dpop-cache-is-write-only`
**File:** lib/msal-browser/src/interaction_client/PlatformAuthInteractionClient.ts
**Step:** review-fresh-eyes | **Action:** fix | **Confidence:** high

A broker DPoP request without caller-supplied popKid skips cache lookup because keyId is populated only later in prepareDpopBrokerRequest. Successful L1 responses are nevertheless cached under the newly generated key and that key is retained, but no mapping carries it into a later request; every later request again has no keyId, skips the cache, provisions another key, and calls the broker. This makes the documented generated-key L1 cache path effectively write-only. Resolve/reuse the generated cache partition before deciding whether cache lookup is possible, or avoid retaining/caching generated entries that cannot be addressed.

### 🟡 `l1-dpop-cache-partitions-evict-each-other`
**File:** lib/msal-browser/src/interaction_client/PlatformAuthInteractionClient.ts
**Step:** review-logic | **Action:** fix | **Confidence:** high

An L1 DPoP broker response still clears the entire account token context before saving its key-partitioned access token. Disable whole-account clearing for cacheable DPoP responses and replace only the matching key partition.

### 🟡 `legacy-dpop-keys-no-longer-removed`
